# Codex 生图素材工作流

## 定位

Codex 图片生成是**上游素材来源**；本仓库负责把原始图变成可重复、可检查、
可发布的游戏资产。该分层借鉴了“生成、加工、运行验证分开”的工作方式，
但不依赖第三方生成器、付费 API 或项目脚手架。

```text
Codex 图片生成 → input/codex/<asset-id>/ → 本仓库确定性工具 → output/<asset-id>/
                                                                    ↓
                                                     游戏仓库的正式资产 + 运行证据
```

不得把生成器直接输出的 PNG/视频帧复制到游戏正式目录；先完成对应类型的
后处理和验收，才可以发布。

## 输入与台账

每个资产使用稳定的 `<asset-id>`，建立下列目录：

```text
input/codex/<asset-id>/
├── prompt.md       # 完整提示词、读取顺序、不可协商规格
├── reference.png   # 可选；身份或风格参考
├── <asset-id>.png  # Codex 原始输出；文件名决定 output/<asset-id>/，不要覆盖
└── notes.md        # 候选淘汰理由、人工复核记录
```

在仓库根的 `assets-manifest.json` 登记资产；首次可从
`assets-manifest.example.json` 复制。台账必须包含：来源、原图与提示词路径、
参考图、游戏内目标尺寸、加工命令、联络表/报告、运行时证据和发布状态。

静态旧流水线的 `source.provider` 写 `codex-imagegen`；逐帧宿主路线写
`codex-builtin-imagegen`，复用/编排则记录实际来源，不冒充新生图。如平台不提供可核对的用量，
`source.cost` 写 `platform-included-or-unknown`，不要虚构金额。

`input/codex/**` 是专门放行的受版本控制目录；其他 `input/*` 仍保持忽略。
`output/` 是可重复生成的临时产物，不提交。最终人工通过的运行截图或短录屏复制到
`evidence/<asset-id>/`，台账的 `runtimeEvidence` 必须指向该受版本控制路径。

逐帧任务使用 `motion_generation.py` 的 job/attempt目录保存原始版本、真实提示词、
参考顺序与审查；这是上述输入台账的具体扩展。代理预览证据可在docs/validation中保留，
但不是正式游戏入库证据，也不自动满足上述发布闸门。入门见
[角色动作使用入口](CHARACTER_MOTION_QUICKSTART.md)。

## 选择正确的生产线

| 资产类型 | 上游输出 | 必经处理 | 允许发布的条件 |
| --- | --- | --- | --- |
| 静态道具、图标、卡牌 | 1 张单图或规则网格 | `slice_grid.py` / `cutout.py` / `resize.py` / `contact.py` | 透明边缘、尺寸与风格在联络表中通过人工检查 |
| 横版角色/敌人动作（旧动作表） | 每动作一张 2×2、`#FF00FF` 背景源网格 | 游戏侧动作表打包器 | 共用缩放与脚底基准线；不触边；播放与朝向人工通过 |
| GPT逐帧二维动作 | 固定画布的实际透明原画，每帧明确姿态 | motion_generation、region_lock/sequence（如需）、collection及消费导出 | 原始版本/提示词可追溯；正常速度全周期、起停与目标游戏动作连接通过 |
| 3D 模型转动作帧 | 透明 GLB/GLTF 或本地 rig | `render_clip_set.py` + `pack_action_sheet.py` | 同一模型、同一正交机位、跨动作归一化与导出校验通过 |

**禁止把视频抽帧当作正式动作资产。** 视频生成的帧间身份、缩放和根节点都可能
漂移；若只作情绪板或临时参考，必须在台账中标记 `status: reference-only`。

## Codex 生成约束

1. 能用同一张身份参考就不要重新描述角色；动作提示词只改变姿态。
2. 旧网格流水线使用纯色背景和明确抠图；GPT逐帧路线请求真实透明背景，并检查alpha。
   不请求画出来的“透明棋盘格”，没有alpha的图不能当透明原画导入。
3. 旧游戏动作表路线采用方形2×2四帧并明确读取顺序。逐帧路线不强制网格：
   每帧独立导入，由工具按明确矩形与时长打包；不猜格子，不把prepare当生成。
4. 明确目标显示尺寸。小于 96px 的图标需使用粗轮廓、简化形状，并在真实尺寸联络表中检查。
5. 生成失败或漂移时保留原图和淘汰理由；不能用逐帧裁切、逐帧缩放掩盖问题。

## 发布前闸门

1. 原图、提示词和参考图可定位，台账已更新。
2. 确定性命令可从原图重复运行；输出目录不靠手工覆盖修图。
3. 先看 `contact_cutouts.png` 和 `contact_resized.png`；透明残留、切格错误、
   风格跑偏必须在此阶段拦下。
4. 动作资产额外检查跨帧统一缩放、脚底线、触边、独立碎片和朝向；脚底线不是
   “看起来差不多”，而是目标项目声明的精确坐标。
5. 在消费游戏运行后保存截图或短录屏路径到 `runtimeEvidence`；构建通过不能替代
   运行证据。

以装备图标试点为例，完整命令应写入台账，不能只记一个缺少输入和尺寸的参数片段：

```bash
python src/run.py \
  input/codex/frontier-equipment-icons-v1/frontier-equipment-icons-v1.png \
  -r 2 -c 2 --size 64 --chroma --tolerance 45
```

## 不属于本仓库的职责

本仓库不管理 API 密钥、不执行有付费风险的自动生图、不决定游戏内数值或动画
判定窗口。生成授权由调用方确认；游戏仓库决定最终动作行序、运行时倍率与验收房间。
